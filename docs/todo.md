# 남은 작업

## 이미지 API

실제 HTTP·MySQL·개발 R2 검사로 재현한 항목이다. 재현 방법은 [이미지 API 기능 검사](image-api-tests.md)를 따른다.

- 우선: 갤러리의 설명·공개 여부만 수정해도 `ClubGalPhotoService.updateMyGalPhotoRecord`가 기존 객체를 삭제한다. 새 이미지가 없으면 기존 객체를 유지하고 해당 회귀 검사를 통과시킨다.
- 우선: 프로필·동아리 대표·갤러리·공지·홍보 사진 교체에서 DB UPDATE 실패 시 이전 객체가 이미 삭제되고 새 객체가 남는다. DB commit 이후 이전 객체 삭제, rollback 시 새 객체 정리, 정리 자체의 실패 처리까지 설계한다. `save()` 호출 성공과 실제 transaction commit 성공을 구분한다.
- 우선: 홍보 사진 삭제 후 재첨부가 `promo_photo(promo_id,is_current)` 유일성 제약으로 HTTP 400이 된다. 소프트 삭제 행의 재사용 또는 스키마·현재 사진 관리 방식을 함께 정리한다. 개발·운영 DB에 동일 제약이 존재한다.
- 업로드 공통 검증: 프로필·동아리·갤러리·홍보·공지 생성·관리자 업로드가 `.txt`/`text/plain`을 저장한다. 빈 갤러리 사진도 생성된다. 이미지 형식·내용·크기·빈 파일 정책을 공통 적용하고 기존 정상 이미지와 호환성을 검사한다.
- 오류 응답 정리: 비로그인 동아리·갤러리·홍보·관리자 업로드는 401 대신 400, 일반 회원의 관리자 이미지 API 및 타인의 홍보 변경은 403 대신 400, 잘못된 이미지 경로·확장자는 400 대신 403을 반환한다. 권한 차단 자체와 응답 상태코드 문제를 구분한다.

## 운영 후속 확인

- 프론트 담당자 배포가 준비되면 카카오 로그인·콜백·화면의 이미지 흐름을 함께 검증한다. 프론트 수정은 현재 백엔드 작업 범위 밖이다.
- 전환 후 남은 S3 참조와 삭제된 객체의 공개 URL·CDN 캐시를 확인하고, 관찰 기간 이후 원본 정리와 이전용 권한 회수를 진행한다.
