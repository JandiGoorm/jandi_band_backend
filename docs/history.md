# 변경 이력

## 2026-10-10
- 보안 공지 영향 버전을 갱신하기 위해 Spring Boot를 3.5.16, springdoc을 2.8.17로 올렸다. Docker 테스트와 실행 이미지 빌드, 호스트 HTTP의 OpenAPI 응답을 확인했다. 서버의 실행 이미지는 PR 병합·배포 전까지 기존 버전을 유지한다.
- Redis Cloud 대신 OCI ARM에 운영·개발 Redis 8.6.7 컨테이너를 각각 배치했다. 전환 직전 앱 쓰기를 중단한 상태에서 원격 DB 0의 키가 0개임을 확인하고 백업했다. 기존 앱 이미지와 JWT 키는 유지했다.
- Redis 컨테이너·비밀번호·영속 볼륨을 환경별로 분리하고 호스트 포트 공개 없이 기존 Docker 내부 네트워크로 연결했다. 실제 적용되지 않던 운영·개발 논리 DB 번호 설정을 제거했다.
- AOF/RDB, noeviction, 메모리·CPU·로그 상한, 비인증 접근 차단을 적용했다. 재시작 후 값과 TTL 보존, 다른 환경 비밀번호 거부, 운영·개발 앱의 Redis 연결과 토큰 차단 기록 조회를 검증했다. 일회성 검사 키는 삭제했다.
- 서버와 사용자의 로컬 환경 파일에서 Redis 연결 설정을 동기화하고 이전 파일을 보존했다. 비밀값은 Git과 Notion에 기록하지 않았다. 원격 Redis 계정 삭제는 사용자 작업으로 남겼다.
- Docker 테스트 500건 통과·기존 비활성 12건 건너뜀, 로컬 호스트 HTTP에서 Redis 읽기/쓰기·내 동아리 조회·OpenAPI 200을 확인했다. 원격 앱에서도 동아리 조회 200과 블랙리스트 조회 후 refresh 401을 검증했다. 이번 서버 전환에는 로컬 브랜치의 JWT·Spring Boot 수정 이미지를 배포하지 않았다.

## 2026-10-09
- 토큰 재발급에서 액세스 토큰을 거부하고 리프레시 쿠키의 밀리초 설정을 초 단위 `Max-Age`로 변환했다. 기존 JWT 형식과 API 요청·응답 스키마를 유지했다.
- 인증 통합 테스트에서 수정 전 액세스 토큰 재발급 허용과 쿠키 수명 오류를 재현했다. 수정 후 Docker 테스트 500건 통과·기존 비활성 12건 건너뜀, 호스트 HTTP 검사 5건 통과를 확인했다. 재발급 거부 이후에도 정상 액세스 인증이 유지된다.
- 이미지 API에서 재현한 갤러리 메타데이터 수정 시 파일 삭제, DB rollback 시 이전 파일 손실·새 파일 잔류, 홍보 사진 제거 후 재첨부 실패, 잘못된 이미지 수용과 오류 상태코드를 수정했다. 기존 서비스 구조를 유지하고 파일 검증·트랜잭션 완료 후 정리·대상 행 잠금만 추가했다. DB 스키마는 변경하지 않았다.
- R2 전용 설정으로 전환하고 AWS 자격증명 fallback·기존 버킷/주소 기본값·이전 URL 별칭·일회성 이전 도구를 제거했다. 자체 클래스는 R2 이름으로 맞췄으며, R2 호환 통신용 AWS SDK v2는 유지했다.
- 최종 수정본의 Docker 단위·통합 테스트 498건이 통과했고 기존 비활성 12건은 건너뛰었다. Docker 백엔드·임시 MySQL/Redis·실제 개발 R2 검사 254건이 모두 통과했다. 동시 이미지 교체, 갤러리 고정·공지 상태 변경과 사진 교체 동시 실행, commit 후 삭제 장애의 502 응답도 포함한다. 카카오 HTTP 응답만 테스트 제공자를 사용했다.
- 최종 검사에서 시도한 객체 key 59개를 정리하고 기존 R2 객체 136개의 목록·크기·ETag가 유지됨을 확인했다. 결과는 `build/image-api-tests/result-cceb51b7f2.json`에 남겼다. 호스트에서 목록 조회 200·미인증 업로드 401을 확인했고 운영 JAR에 테스트 서버·MockWebServer·테스트 DB가 포함되지 않음을 검사했다.
- S3 원본 136개·R2·로컬 백업의 크기와 SHA-256이 모두 일치했다. 운영 DB의 활성 R2 참조 44건에 누락이 없고 활성 S3 참조는 0건이다. 남은 S3 URL 15건은 원본 객체가 이미 없는 비활성 사진 이력이다. 이 확인은 읽기 전용이며 실제 S3 버킷 삭제는 하지 않았다. 이번 오류 수정본의 운영 배포는 별도 병합·배포 확인이 필요하다.

- 프론트엔드 없이 이미지 API 10개 시나리오를 Docker 백엔드·MySQL 8.4·Redis·실제 개발 R2에서 실행했다. 앱 API 요청 162건과 검사 209건 중 170건 통과, 39건 실패를 기록했다. 39건은 독립된 버그 개수가 아니라 파일 보존·정리·HTTP 상태 등을 나눈 실패 검사 수다. 카카오 응답만 테스트 제공자로 대체했고 앱의 로그인·가입·재로그인·토큰 갱신은 실제 API를 사용했다.
- 갤러리 메타데이터 수정 시 파일 삭제, 다섯 도메인의 DB rollback과 R2 불일치, 홍보 사진 제거 후 재첨부 제약 오류, 잘못된 파일 수용, 오류 상태코드 불일치를 재현했다. 도메인 기능 코드는 변경하지 않고 재현 테스트와 TODO를 추가했다. 운영·개발 DB의 홍보 사진 유일성 제약은 읽기 전용으로 확인했다.
- 확장 검사에서 시도한 객체 키 46개를 정리하고 기존 R2 객체 136개의 키·크기·ETag와 전체 목록이 원래대로 유지됨을 확인했다. 테스트 DB와 회원은 로컬 임시 컨테이너에만 생성했다. 전체 Gradle 검사는 489건 통과, 기존 비활성 12건으로 끝났다. 상세 결과는 `build/image-api-tests/result-b7d201e165.json`에 남겼다.

- 운영 배포 후 이미지 쓰기와 삭제 배치를 멈추고 최신 객체·DB 백업을 검증한 뒤 이미지 주소 74행과 앱 설정을 R2로 전환했다. DB 26개 테이블의 이미지 주소 외 데이터는 변경되지 않았다. 기존 이미지 공개 조회, 인증된 특수문자 경로 업로드·삭제 후 404, 동아리·홍보 API의 새 이미지 주소를 검증했다.
- 개발 배포의 실제 S3 업로드 검증에서 리터럴 `+` 공개 주소가 403, `%2B` 주소가 200임을 확인했다. URL 생성에서 `+`를 인코딩하고 기존 URL 왕복 테스트와 HTTP 검증에 회귀 검사를 추가했다.
- 수정본을 개발 서버에 배포하고 S3와 R2에서 한글·공백·`+`·`%` 경로의 인증 업로드·공개 조회·바이트/Content-Type 대조·외부/기본 사진 보호·삭제를 검증했다. S3에서 삭제 후 목록에 객체가 없음을 확인했고, R2는 공개 URL 404도 확인했다. 검증 후 임시 계정·객체를 정리하고 개발 환경을 R2로 복귀했다.
- AWS SDK Java v2와 S3/R2 공통 설정을 도입했다. 기존 AWS 환경변수와 S3 기본 주소의 호환성을 유지했다.
- 공개 이미지 URL 생성·이전 URL 판별을 통합하고 외부 이미지·공용 기본 객체의 삭제를 막았다.
- SDK 서명·전송에 필요한 반복 가능한 multipart 스트림을 제공하고, 실제 HTTP 및 되감기를 지원하지 않는 1MiB 스트림으로 확인했다.
- Docker 테스트 501건 중 489건 통과, 기존 비활성 테스트 12건은 건너뛰었다. 호스트의 인증된 HTTP 업로드·바이트/Content-Type 조회·외부/기본 이미지 보호·이전 URL 삭제·삭제 후 404를 검증했다.
- DB URL dry-run·조건부 적용·역변환과 일회성 객체 복사·논리 백업 도구를 추가했다. MySQL에서 3개 통합 테스트로 재실행, 전체 트랜잭션 취소, 누락 객체 차단과 URL 판별을 검증했다.
- 실제 개발 R2에 연결한 Docker 백엔드의 인증된 HTTP 업로드·공개 조회·바이트/Content-Type 대조·기본/외부 사진 보호·기존 S3 주소를 이용한 삭제·최종 404를 검증했다. CDN 캐시로 삭제 후 사진이 남는 문제는 인프라의 이미지 전용 캐시 우회 규칙으로 해결했다.
- 개발 설정·DB URL 이전 도구를 `docs/image-storage.md`로 모았다. Notion에는 버킷·도메인 매핑·백업 위치·운영 절차만 남긴다.
- 완료된 Tailscale 개발·운영 전환 항목을 TODO에서 정리했다.
- Tailscale 연결 옵션 중복을 제거하고, 연결 후 별도 명령으로 실행기의 서브넷 경로 수신을 해제했다.
